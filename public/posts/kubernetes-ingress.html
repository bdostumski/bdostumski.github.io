2. Understand Ingress Architecture

Ingress provides HTTP/HTTPS routing from outside the cluster to Kubernetes Services. 


            Internet
               |
               |
           DNS Record
               |
               |
        Load Balancer
               |
               |
        Ingress Controller
               |
     +---------+---------+
     |                   |
  /api                 /web
     |                   |
API Service         Web Service
     |                   |
  API Pods            Web Pods

Important components:

Component Responsibility
Ingress Defines HTTP/HTTPS routing rules
Ingress Controller Implements routing rules
IngressClass Identifies the controller
Service Provides access to backend Pods
DNS Resolves application hostnames
TLS Secret Stores certificate and private key
LoadBalancer Exposes the controller externally

Note: Creating an Ingress resource alone does not expose an application. An appropriate Ingress Controller must be installed and configured.

4. Create a Basic Ingress Resource 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80



# Apply Ingress configuration
kubectl apply -f ingress.yaml

# List Ingress resources
kubectl get ingress

# Inspect Ingress
kubectl describe ingress web-ingress

# Display Ingress YAML
kubectl get ingress web-ingress -o yaml

# Delete Ingress
kubectl delete ingress web-ingress

Note: The example assumes an IngressClass named `nginx` already exists and is managed by a compatible controller.

5. Host-Based Routing

Host-based routing directs requests to different Services according to the HTTP hostname. 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: host-based-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80

    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: backend-service
                port:
                  number: 8080

    - host: admin.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: admin-service
                port:
                  number: 80



# Inspect host routing rules
kubectl describe ingress host-based-ingress

# Test frontend hostname
curl -I http://app.example.com

# Test API hostname
curl -I http://api.example.com

# Test admin hostname
curl -I http://admin.example.com

7. Ingress Path Types

Kubernetes supports three path types.

Path Type Behavior Example
`Prefix` Matches path elements and their subpaths `/api` matches `/api/users`
`Exact` Matches the exact URL path `/api` matches `/api` only
`ImplementationSpecific` Matching behavior depends on the controller Controller-specific 

rules:
  - host: example.com
    http:
      paths:
        - path: /api
          pathType: Prefix
          backend:
            service:
              name: api-service
              port:
                number: 8080

        - path: /health
          pathType: Exact
          backend:
            service:
              name: health-service
              port:
                number: 80

Important:

  • `Prefix` is case-sensitive.
  • Prefix matching uses path elements, not arbitrary string prefixes.
  • `/api` matches `/api/users`.
  • `/api` does not match `/apiv2`.
  • `Exact` requires an exact path match.

8. Configure TLS / HTTPS

Ingress TLS configuration references a Kubernetes Secret containing a certificate and private key. 


# Create TLS secret
kubectl create secret tls app-tls \
  --cert=tls.crt \
  --key=tls.key \
  -n production

# List secrets
kubectl get secrets -n production

# Inspect TLS secret
kubectl describe secret app-tls -n production

# Display TLS secret type
kubectl get secret app-tls \
  -n production \
  -o jsonpath='{.type}'

# Inspect certificate expiration locally
openssl x509 -in tls.crt -noout -dates

Example Ingress: 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: secure-ingress
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80



# Apply TLS Ingress
kubectl apply -f secure-ingress.yaml

# Inspect TLS configuration
kubectl describe ingress secure-ingress

# Test HTTPS endpoint
curl -I https://app.example.com

# Inspect certificate served by endpoint
openssl s_client \
  -connect app.example.com:443 \
  -servername app.example.com </dev/null

# Inspect certificate details
echo | openssl s_client \
  -connect app.example.com:443 \
  -servername app.example.com 2>/dev/null \
  | openssl x509 -noout -dates -issuer -subject

Note: TLS secrets must exist in the same namespace as the Ingress resource. TLS termination and HTTP-to-HTTPS redirection behavior depend on the selected controller.

9. HTTP to HTTPS Redirect

HTTP-to-HTTPS redirection is commonly configured through controller-specific settings.

For the community ingress-nginx controller, the legacy annotation was: 


metadata:
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"

Example: 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: redirect-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - app.example.com
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service
                port:
                  number: 80



# Test HTTP redirect
curl -I http://app.example.com

# Follow redirects
curl -IL http://app.example.com

# Test HTTPS
curl -I https://app.example.com

Note: Annotations are controller-specific. Do not assume this annotation works with other controllers.

10. Wildcard Host Routing

Wildcard hostnames can be used to route multiple subdomains through one Ingress. 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: wildcard-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: "*.example.com"
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: wildcard-service
                port:
                  number: 80



# Test application subdomain
curl -I http://app.example.com

# Test API subdomain
curl -I http://api.example.com

# Test wildcard hostname resolution
nslookup app.example.com

# Inspect Ingress
kubectl describe ingress wildcard-ingress

Note: Kubernetes wildcard host matching covers one DNS label, not arbitrary nested subdomains. DNS records and controller support must also be configured.

13. DNS Configuration & Validation

Ingress hostnames must resolve to the externally reachable Ingress Controller endpoint. 


# Resolve DNS
nslookup app.example.com

# Query DNS records
dig app.example.com

# Display DNS A record
dig app.example.com A

# Display DNS CNAME
dig app.example.com CNAME

# Check DNS propagation through a resolver
dig @8.8.8.8 app.example.com

# Test HTTP hostname routing
curl -v http://app.example.com

# Test HTTPS hostname routing
curl -v https://app.example.com

# Test a hostname against a specific IP
curl -H "Host: app.example.com" http://<ingress-ip>

14. Test Ingress Without DNS

You can test routing before public DNS records are configured by sending the appropriate Host header. 


# Test HTTP using Host header
curl -v \
  -H "Host: app.example.com" \
  http://<ingress-ip>

# Test HTTPS with hostname and SNI
curl -vk \
  --resolve app.example.com:443:<ingress-ip> \
  https://app.example.com

# Test a specific URL path
curl -v \
  --resolve app.example.com:443:<ingress-ip> \
  https://app.example.com/api

### 16. Configure Request Path Rewriting

Path rewriting is controller-specific and is not part of the standard Ingress API.

Example using the legacy community ingress-nginx annotation: 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rewrite-ingress
  annotations:
    nginx.ingress.kubernetes.io/use-regex: "true"
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /api(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: api-service
                port:
                  number: 8080

Example: 


External request:
https://app.example.com/api/users

Backend request:
/users



# Inspect rewrite configuration
kubectl describe ingress rewrite-ingress

# Test rewritten path
curl -v https://app.example.com/api/users

# Inspect controller logs
kubectl logs deployment/ingress-nginx-controller \
  -n ingress-nginx

Note: Regex syntax and rewrite behavior depend on the controller. Validate the exact implementation before using this configuration.

17. Configure Timeouts & Request Body Size

Ingress proxies commonly provide settings for request size and connection timeouts.

Legacy ingress-nginx annotations: 


metadata:
  annotations:
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "10"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"

# Inspect Ingress annotations
kubectl get ingress <ingress-name> -o yaml

# Inspect controller configuration
kubectl get configmap -n ingress-nginx

# Inspect controller ConfigMap
kubectl describe configmap ingress-nginx-controller \
  -n ingress-nginx

# Inspect controller logs

Note: Annotation names and supported values vary by controller. Large request bodies and long timeouts should be configured according to application requirements and resource capacity.

    nginx.ingress.kubernetes.io/limit-burst-multiplier: "5"
    nginx.ingress.kubernetes.io/whitelist-source-range: "10.0.0.0/8,192.168.0.0/16"



# Inspect configured annotations

Note: Rate limiting and source IP restrictions are implementation-specific. Correct client IP detection requires a trusted proxy/load balancer configuration. Do not trust arbitrary forwarded headers from untrusted clients.

19. Configure CORS

CORS can be handled by the application or by an Ingress Controller.

Legacy ingress-nginx example: 


metadata:
  annotations:
    nginx.ingress.kubernetes.io/enable-cors: "true"
    nginx.ingress.kubernetes.io/cors-allow-origin: "https://frontend.example.com"
    nginx.ingress.kubernetes.io/cors-allow-methods: "GET, POST, PUT, DELETE, OPTIONS"
    nginx.ingress.kubernetes.io/cors-allow-headers: "Authorization, Content-Type"
    nginx.ingress.kubernetes.io/cors-allow-credentials: "true"



# Test CORS preflight request
curl -i -X OPTIONS \
  https://api.example.com \
  -H "Origin: https://frontend.example.com" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: Authorization,Content-Type"

# Inspect response headers
curl -I \
  -H "Origin: https://frontend.example.com" \
  https://api.example.com

Note: When credentials are enabled, wildcard origins should not be used. Configure an explicit trusted origin.

20. Configure Canary Deployments

Canary routing sends a subset of requests to a new application version.

Legacy ingress-nginx example: 


apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: app-v2-service
                port:
                  number: 80

The primary Ingress routes to `app-v1-service`, while the canary Ingress routes a configured portion of traffic to `app-v2-service`. 


# List application Ingress resources
kubectl get ingress

# Inspect canary configuration
kubectl describe ingress app-canary

# Test application endpoint
curl -I https://app.example.com

# Check backend services
kubectl get services

# Monitor application Pods
kubectl get pods -w

Note: Canary annotations and traffic distribution are controller-specific. A weight of 10 is a routing target, not a guarantee of an exact percentage over a small number of requests.

21. Configure Sticky Sessions

Session affinity can help keep a client connected to the same backend instance.

Legacy ingress-nginx example: 


metadata:
  annotations:
    nginx.ingress.kubernetes.io/affinity: "cookie"
    nginx.ingress.kubernetes.io/session-cookie-name: "INGRESSCOOKIE"
    nginx.ingress.kubernetes.io/session-cookie-expires: "172800"
    nginx.ingress.kubernetes.io/session-cookie-max-age: "172800"



# Inspect session affinity configuration
kubectl get ingress <ingress-name> -o yaml

# Display response cookies
curl -I https://app.example.com

# Display cookies on subsequent requests
curl -c cookies.txt -b cookies.txt \
  -v https://app.example.com

Note: Sticky sessions can create uneven backend load. Prefer external session storage when applications need to scale horizontally without relying on a specific Pod.

22. Configure Authentication at Ingress

Authentication can be integrated at the edge using controller-specific mechanisms or an external authentication service.

Legacy ingress-nginx basic authentication example: 


# Create authentication credentials file
htpasswd -c auth admin

# Create Kubernetes Secret
kubectl create secret generic basic-auth \
  --from-file=auth \
  -n production



metadata:
  annotations:
    nginx.ingress.kubernetes.io/auth-type: basic
    nginx.ingress.kubernetes.io/auth-secret: basic-auth
    nginx.ingress.kubernetes.io/auth-realm: "Authentication Required"



# Inspect authentication secret
kubectl describe secret basic-auth -n production

# Test without credentials
curl -I https://app.example.com

# Test with credentials
curl -u admin:<password> \
  -I https://app.example.com

Note: Use a secure credential-generation process and protect Kubernetes Secrets with appropriate RBAC and encryption at rest. For production identity management, consider an established OIDC or external authentication integration.

                  number: 50051

HTTP Status Common causes
404 Host/path mismatch, default backend or controller routing configuration
502 Backend connection failure, invalid upstream protocol or reset
503 No available backend endpoints or controller-specific unavailable response
504 Upstream timeout
301/308 HTTP-to-HTTPS redirection
403 Authentication, authorization or IP restriction

31. Gateway API – Modern Alternative to Ingress

The Kubernetes Ingress API is stable but frozen. Gateway API provides a more expressive, role-oriented model for traffic management.

Important resources:

Resource Purpose
GatewayClass Defines the Gateway controller implementation
Gateway Defines traffic entry points and listeners
HTTPRoute Defines HTTP routing rules
GRPCRoute Defines gRPC routing rules
TLSRoute Defines TLS routing
TCPRoute Defines TCP routing
UDPRoute Defines UDP routing 

# Check Gateway API CRDs
kubectl get crds | grep gateway.networking.k8s.io

# List GatewayClasses
kubectl get gatewayclass

# List Gateways
kubectl get gateways -A

# List HTTPRoutes
kubectl get httproutes -A

# Inspect a Gateway
kubectl describe gateway <gateway-name> -n <namespace>

# Inspect HTTPRoute
kubectl describe httproute <route-name> -n <namespace>

# Inspect Gateway API conditions
kubectl get gateway <gateway-name> \
  -n <namespace> -o yaml

Example Gateway: 


apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: application-gateway
spec:
  gatewayClassName: example-gateway-class
  listeners:
    - name: http
      protocol: HTTP
      port: 80
      allowedRoutes:
        namespaces:
          from: Same

Example HTTPRoute: 


apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: application-route
spec:
  parentRefs:
    - name: application-gateway
  hostnames:
    - app.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: web-service
          port: 80



# Apply Gateway
kubectl apply -f gateway.yaml

# Apply HTTPRoute
kubectl apply -f httproute.yaml

# Inspect Gateway status
kubectl get gateway application-gateway

# Inspect route status
kubectl get httproute application-route

# Check Gateway conditions
kubectl describe gateway application-gateway

# Check route conditions
kubectl describe httproute application-route

Note: A compatible Gateway API implementation and its CRDs must be installed before applying these resources. Replace the example GatewayClass with one supported by your controller.

Beginner

Q1: What is Kubernetes Ingress?

Ingress is a Kubernetes API resource that defines external HTTP/HTTPS routing to services.

Q2: What problem does Ingress solve?

Centralizes Layer 7 routing rules (host/path/TLS) instead of exposing many LoadBalancers.

Q3: Is Ingress a load balancer itself?

No, Ingress is configuration; an Ingress Controller implements it.

Q4: What is an Ingress Controller?

Software that watches Ingress resources and configures a proxy/load balancer accordingly.

Q5: Common Ingress Controllers?

NGINX Ingress, Traefik, HAProxy, cloud-specific controllers, etc.

Q6: What is ingressClassName?

Field selecting which controller should process the Ingress resource.

Q7: Why ingress class matters?

Multiple controllers may exist; class avoids ambiguous ownership.

Q8: What does an Ingress rule contain?

Host, path, backend service name, and service port mapping.

Q9: Host-based routing?

Route by HTTP Host header (e.g., app.example.com).

Q10: Path-based routing?

Route by URL path prefix/exact match (e.g., /api, /admin).

Q11: What backend does Ingress point to?

Kubernetes Service, which forwards traffic to Pods.

Q12: Service vs Ingress?

Service exposes internal app endpoints; Ingress governs external HTTP(S) entry routing.

Q13: What is default backend?

Fallback service for unmatched requests (controller-dependent behavior/config).

Q14: What is TLS in Ingress?

HTTPS termination configuration using certificate secret references.

Q15: What does TLS secret contain?

Certificate and private key (typically type kubernetes.io/tls).

Q16: Can one Ingress handle multiple hosts?

Yes, multiple rules/hosts can be defined.

Q17: What is pathType?

Defines path matching behavior (Exact, Prefix, ImplementationSpecific).

Q18: Prefix vs Exact pathType?

Prefix matches path prefix tree; Exact matches full path exactly.

Q19: What is wildcard host in Ingress?

Host pattern matching subdomains (controller support/constraints apply).

Q20: What is rewrite target concept?

Modify request path before proxying to backend.

Q21: Why path rewrite is used?

Align external URL structure with backend app routes.

Q22: What are annotations in Ingress?

Controller-specific configuration extensions on metadata.

Q23: Annotation risk?

Portability loss and misconfig due to controller-specific semantics.

Q24: What is ingress status address?

External IP/hostname exposed by controller for DNS mapping.

Q25: Why DNS is required with Ingress?

Public hostnames must resolve to controller’s external endpoint.

Q26: What is HTTP vs HTTPS handling?

HTTP can redirect to HTTPS or serve directly depending config.

Q27: What is SSL redirect?

Automatic redirection of HTTP requests to HTTPS.

Q28: What is SNI relevance?

TLS host-based certificate selection for multi-domain ingress endpoints.

Q29: What is 404 from Ingress usually mean?

No matching host/path rule or backend unavailable/misconfigured.

Q30: What is 502/503 from Ingress often indicate?

Backend service/pod not reachable or unhealthy.

Q31: What is readiness probe relation to Ingress?

Only ready pods should receive traffic via Service endpoints.

Q32: What is externalTrafficPolicy relation (Service LB)?

Affects source IP preservation and routing behavior at service edge.

Q33: Can Ingress route TCP/UDP by default spec?

Ingress API is primarily HTTP/HTTPS; TCP/UDP often controller-specific extensions.

Q34: What is beginner anti-pattern with Ingress?

One giant shared Ingress with unmanaged rule sprawl.

Q35: Another beginner anti-pattern?

Exposing apps over HTTP without TLS in production.

Q36: Beginner security baseline?

TLS everywhere, minimal exposed paths, and controlled DNS.

Q37: Beginner reliability baseline?

Health probes and multiple backend replicas.

Q38: Beginner observability baseline?

Access logs, error logs, request latency and status metrics.

Q39: Beginner governance baseline?

Standard naming and ingress class usage conventions.

Q40: What is kubectl describe ingress useful for?

Inspect rules, events, backend mappings, and controller feedback.

Q41: What is ingress event troubleshooting value?

Surface config errors like missing service/secret/class mismatch.

Q42: What is canary concept (ingress-level)?

Route subset of requests to alternate backend version.

Q43: Why canary routing helps?

Validate changes with limited user impact.

Q44: What is sticky session concept?

Route same client repeatedly to same backend (cookie/IP strategies).

Q45: Sticky session tradeoff?

Session affinity convenience vs uneven load distribution risk.

Q46: What is timeout setting in ingress proxy?

Controls connect/read/send request timeout behavior.

Q47: Why timeout tuning matters?

Prevents hanging connections and aligns with app response profiles.

Q48: What is body size limit setting?

Max request payload allowed by ingress proxy.

Q49: Why body limit is important?

Protects resources and prevents unexpected upload failures.

Q50: What is CORS handling relation?

Often configured at app or ingress layer for browser cross-origin control.

Q51: What is rate limiting at ingress?

Throttle requests per client/key to reduce abuse.

Q52: Why rate limiting?

Protect backend capacity and mitigate simple attack traffic.

Q53: What is IP allow/deny listing?

Restrict ingress access to specific client ranges.

Q54: Beginner workflow principle?

Keep routing rules explicit and minimal.

Q55: Beginner architecture principle?

Separate public and internal traffic entry patterns.

Q56: Beginner collaboration principle?

Platform team defines ingress guardrails; app teams define routes.

Q57: Beginner incident principle?

Document common 4xx/5xx ingress triage playbook.

Q58: Beginner scaling principle?

Start with one controller pattern per environment before diversification.

Q59: Beginner compliance principle?

Track certificate ownership and renewal responsibilities.

Q60: Beginner best practice?

Treat ingress config as production-critical code.
