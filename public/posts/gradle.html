4. Gradle Build Lifecycle

Gradle organizes build execution around tasks and their dependency graph.

Common lifecycle tasks:

  • `clean` – Removes generated build files.
  • `assemble` – Creates project artifacts.
  • `check` – Executes verification tasks.
  • `test` – Executes unit tests.
  • `build` – Assembles and verifies the project.
  • `publish` – Publishes configured artifacts.
# Common Gradle lifecycle tasks
./gradlew clean
./gradlew assemble
./gradlew check
./gradlew test
./gradlew build

# Typical build commands
./gradlew clean build
./gradlew clean assemble
./gradlew clean check

Lifecycle differences

Task Purpose
`clean` Remove generated build outputs
`assemble` Create project artifacts
`check` Run verification tasks
`test` Execute unit tests
`build` Assemble and verify project
`publish` Publish configured artifacts

Note: Gradle executes prerequisite tasks automatically according to the task dependency graph. For example, `build` normally depends on `assemble` and `check`.

5. Profiles & Environment Configuration

Gradle supports environment-specific configuration through project properties, system properties, and environment variables. 

# Pass a project property
./gradlew build -Penv=dev

# Use a test environment
./gradlew build -Penv=test

# Use a production environment
./gradlew build -Penv=prod

# Pass multiple project properties
./gradlew build -Penv=dev -Pregion=eu

# Pass a system property
./gradlew test -Dspring.profiles.active=test

# Set an environment variable
SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun

# Pass Spring Boot application arguments
./gradlew bootRun --args='--spring.profiles.active=dev --server.port=8081'

Note: Gradle project properties (`-P`), JVM system properties (`-D`), and environment variables serve different purposes.

10. Debugging – Gradle, Tests & Spring Boot

There are three different debugging scenarios: Gradle build debugging, test debugging, and Java application debugging.

10.1 Gradle Build Debugging 

# Enable detailed Gradle debug logs
./gradlew --debug build
./gradlew --debug test
./gradlew --debug assemble

# Enable informational logs
./gradlew --info build

# Display exception stack traces
./gradlew --stacktrace build

# Display full exception information
./gradlew --full-stacktrace build

# Debug Gradle configuration and execution
./gradlew --info clean build

Difference:

Command Purpose
`–debug` Detailed Gradle debug logs
`–info` Informational build logs
`–stacktrace` Display exception stack traces
`–full-stacktrace` Display full stack traces

10.2 Debug Unit & Integration Tests 

# Enable test debugging
./gradlew test --debug-jvm

# Enable test debugging with a specific task
./gradlew integrationTest --debug-jvm

# Run a specific test with debugging
./gradlew test --tests UserServiceTest --debug-jvm

The test JVM normally waits for a debugger connection on port `5005`.

10.3 Start Spring Boot in Debug Mode 

# Option 1 – Start Spring Boot with debugging enabled
./gradlew bootRun \
  --debug-jvm

# Option 2 – Configure a custom debug port
./gradlew bootRun \
  --debug-jvm \
  -Dorg.gradle.debug=true

For more control, configure the Spring Boot application JVM arguments directly: 

# Start application with JVM debugging
JAVA_TOOL_OPTIONS="-agentlib:jdwp=transport=dt_socket,server=y,suspend=y,address=*:5005" \
  ./gradlew bootRun

Note: `–debug-jvm` on a `Test` task debugs the test JVM. It does not automatically debug the Spring Boot application started by `bootRun`.

10.4 Connect IntelliJ IDEA / Eclipse Debugger

Create a Remote JVM Debug configuration.

Setting Value
Host `localhost`
Port `5005`
Debugger mode Attach to remote JVM
Transport Socket

Steps:

  1. Start the application or test JVM with debugging enabled.
  2. Create or select the Remote JVM Debug configuration in your IDE.
  3. Connect to `localhost:5005`.
  4. Set breakpoints in your Java code.
  5. Send a request to your application.
  6. Execution stops at the breakpoints.

10.5 Understand JVM Debugging Parameters 

-agentlib:jdwp=transport=dt_socket,server=y,suspend=y,address=*:5005
Parameter Meaning
`transport=dtsocket` Use socket communication
`server=y` JVM listens for debugger connections
`suspend=y` Wait for debugger before starting
`suspend=n` Start application immediately
`address=*:5005` Listen on port 5005 on available interfaces

Security: Debug ports allow powerful control over the JVM. Restrict them to localhost or a trusted network. Never expose port 5005 publicly.

10.6 Quick Debugging Cheat Sheet

12. Gradle Performance & Build Cache

Gradle provides several features to improve build performance, including the daemon, incremental builds, configuration cache, and build cache. 

# Enable Gradle daemon
./gradlew build --daemon

# Enable build cache
./gradlew build --build-cache

# Enable configuration cache
./gradlew build --configuration-cache

# Enable parallel execution
./gradlew build --parallel

# Limit workers
./gradlew build --max-workers=4

# Display task execution information
./gradlew build --profile

# Generate a build scan (requires scan service/setup)
./gradlew build --scan

Useful performance options

Option Purpose
`–daemon` Use Gradle daemon
`–build-cache` Reuse cached task outputs
`–configuration-cache` Cache build configuration
`–parallel` Run independent projects concurrently
`–max-workers` Control worker count
`–profile` Generate build performance report
`–scan` Generate detailed build diagnostics

Note: Build cache and configuration cache are different features. The former caches task outputs; the latter caches the configured build model.

Beginner

Q1: What is Gradle?

Gradle is a flexible build automation tool supporting JVM and many other ecosystems.

Q2: Why use Gradle?

It provides fast incremental builds, rich dependency management, and programmable build logic.

Q3: Gradle vs Maven in one line?

Maven is convention-heavy and phase-based; Gradle is task-graph-based and highly customizable.

Q4: What is a build script in Gradle?

Configuration file defining plugins, dependencies, tasks, and build logic.

Q5: Main Gradle DSL options?

Groovy DSL (build.gradle) and Kotlin DSL (build.gradle.kts).

Q6: What is settings file in Gradle?

settings.gradle(.kts) defines root project name and included subprojects.

Q7: What is a task in Gradle?

A unit of work (compile, test, jar, custom action).

Q8: What is task graph?

Directed graph of tasks and dependencies Gradle executes.

Q9: What does gradle tasks show?

Available tasks in the project.

Q10: What does gradle build do?

Runs lifecycle tasks to compile, test, and assemble artifacts.

Q11: What does gradle clean do?

Deletes build outputs (usually build/ directories).

Q12: What does gradle test do?

Executes test tasks.

Q13: What does gradle assemble do?

Builds artifacts without running all verification tasks.

Q14: What does gradle check do?

Runs verification tasks (tests, static checks).

Q15: What does gradle dependencies do?

Displays dependency tree for configurations.

Q16: What is a plugin in Gradle?

Reusable build logic that adds tasks/configurations/conventions.

Q17: Common core plugins?

java, application, jacoco, maven-publish, checkstyle.

Q18: What does Java plugin provide?

Standard Java source sets, compile/test/jar tasks, dependency configurations.

Q19: What are source sets?

Logical groups of sources/resources (main, test, custom).

Q20: Default source directories in Java plugin?

src/main/java, src/test/java, resources equivalents.

Q21: What is repository in Gradle?

Source location for resolving dependencies/plugins (Maven Central, internal repos).

Q22: What is dependency notation?

Usually group:name:version coordinates.

Q23: What is configuration in Gradle?

Named dependency bucket with specific usage semantics.

Q24: Common configurations?

implementation, api, compileOnly, runtimeOnly, testImplementation.

Q25: implementation vs api (java-library)?

api leaks to consumers; implementation is internal to module.

Q26: What is transitive dependency?

Dependency brought indirectly through another dependency.

Q27: Why can transitive dependencies be risky?

Version conflicts and hidden classpath changes.

Q28: What is Gradle Wrapper?

Project-local scripts and metadata pinning Gradle version.

Q29: Why use Wrapper?

Consistent Gradle version across all developers/CI.

Q30: Wrapper commands?

./gradlew <task> (Unix), gradlew.bat <task> (Windows).

Q31: What is Gradle daemon?

Background process speeding up subsequent builds.

Q32: Why daemon improves performance?

Reuses JVM and cached build state between runs.

Q33: What is incremental build?

Only re-running tasks whose inputs/outputs changed.

Q34: What is up-to-date check?

Gradle mechanism skipping task if inputs/outputs unchanged.

Q35: What is build cache?

Reuses task outputs from local/remote cache when inputs match.

Q36: Local vs remote build cache?

Local on machine; remote shared across team/CI.

Q37: What is --info and --debug?

More verbose logging levels for troubleshooting.

Q38: What is --stacktrace?

Prints full exception stack traces on build failures.

Q39: What is --scan?

Publishes build scan with detailed performance and diagnostics (service/setup dependent).

Q40: What is configuration phase?

Gradle evaluates build scripts and configures tasks.

Q41: What is execution phase?

Selected tasks are executed according to task graph.

Q42: Why avoid heavy work during configuration?

Slows every build invocation, even unrelated tasks.

Q43: What is lazy task configuration?

Deferring task creation/config until needed.

Q44: What APIs support lazy configuration?

tasks.register and Provider API patterns.

Q45: register vs create task?

register is lazy; create is eager.

Q46: What is ext/property in Gradle?

Extra project properties for sharing values in scripts.

Q47: What is gradle.properties?

File for build properties/JVM args/settings at project/user level.

Q48: What is org.gradle.jvmargs used for?

Configure JVM options for Gradle daemon.

Q49: What is common beginner Gradle anti-pattern?

Copying large script blocks without understanding task/config impacts.

Q50: Another beginner anti-pattern?

Using dynamic dependency versions in production builds.

Q51: Why avoid dynamic versions (e.g., 1.+)?

Hurts reproducibility and can cause surprise breakages.

Q52: What is dependency lock concept?

Pin resolved versions for reproducible dependency graphs.

Q53: Beginner security baseline?

Trusted repositories, pinned versions, wrapper verification practices.

Q54: Beginner CI baseline?

Run ./gradlew clean build with wrapper in pipeline.

Q55: Beginner performance baseline?

Enable daemon/build cache and avoid unnecessary clean builds.

Q56: What is task dependency declaration?

Using dependsOn to enforce execution prerequisites.

Q57: MustRunAfter vs dependsOn?

Ordering hint vs actual dependency requirement.

Q58: finalizedBy usage?

Run cleanup/finalizer task after another task, even on failure scenarios.

Q59: Beginner project structure principle?

Keep build scripts small and readable; move shared logic out when needed.

Q60: Beginner best practice?

Use wrapper, pin versions, and lean on conventions before custom complexity.
