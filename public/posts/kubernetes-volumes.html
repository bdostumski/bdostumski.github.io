Kubernetes Volumes Command Handbook

1. Inspect Pod Volumes and Mounts


# List pods
kubectl get pods

# Inspect a pod's volume definitions and mounts
kubectl describe pod <pod-name>

# Print the complete pod specification
kubectl get pod <pod-name> -o yaml

# Inspect only volume definitions
kubectl get pod <pod-name> \
  -o jsonpath='{.spec.volumes}'

# Inspect container volume mounts
kubectl get pod <pod-name> \
  -o jsonpath='{.spec.containers[*].volumeMounts}'

# Inspect volumes in a specific namespace
kubectl get pods -n <namespace> -o wide

2. Create and Inspect an emptyDir Volume

An `emptyDir` volume is created when a Pod is assigned to a node. It survives container restarts but is deleted when the Pod is removed. 


apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  containers:
    - name: writer
      image: busybox
      command: ["sh", "-c", "while true; do date >> /data/time.log; sleep 10; done"]
      volumeMounts:
        - name: shared-data
          mountPath: /data

  volumes:
    - name: shared-data
      emptyDir: {}



# Create the pod
kubectl apply -f emptydir.yaml

# Inspect the volume
kubectl describe pod emptydir-demo

# Read files from the mounted volume
kubectl exec emptydir-demo -- cat /data/time.log

# List mounted files
kubectl exec emptydir-demo -- ls -lah /data

# Delete the pod (the emptyDir data is removed)
kubectl delete pod emptydir-demo

3. Configure emptyDir Size and Memory

Use `sizeLimit` to limit the amount of storage an `emptyDir` can consume. 


volumes:
  - name: cache
    emptyDir:
      sizeLimit: 1Gi

For memory-backed temporary storage: 


volumes:
  - name: memory-cache
    emptyDir:
      medium: Memory
      sizeLimit: 256Mi

Memory-backed `emptyDir` uses tmpfs. Its contents consume memory and count against the memory limits of the writing container.

4. Share a Volume Between Containers

Containers in the same Pod can mount the same volume at different paths. 


apiVersion: v1
kind: Pod
metadata:
  name: shared-volume-demo
spec:
  containers:
    - name: writer
      image: busybox
      command: ["sh", "-c", "while true; do date >> /shared/log.txt; sleep 5; done"]
      volumeMounts:
        - name: shared
          mountPath: /shared

    - name: reader
      image: busybox
      command: ["sh", "-c", "while true; do cat /data/log.txt; sleep 10; done"]
      volumeMounts:
        - name: shared
          mountPath: /data
          readOnly: true

  volumes:
    - name: shared
      emptyDir: {}



# Inspect both containers
kubectl describe pod shared-volume-demo

# Read data from the reader container
kubectl exec shared-volume-demo -c reader -- cat /data/log.txt

# Inspect the writer container
kubectl exec shared-volume-demo -c writer -- ls -lah /shared

5. Mount a ConfigMap as Files 


# Create a ConfigMap
kubectl create configmap app-config \
  --from-literal=APP_MODE=production \
  --from-literal=LOG_LEVEL=info

# Inspect it
kubectl describe configmap app-config

# Display its YAML
kubectl get configmap app-config -o yaml

Pod example: 


apiVersion: v1
kind: Pod
metadata:
  name: config-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "cat /etc/app-config/APP_MODE; sleep 3600"]
      volumeMounts:
        - name: app-config
          mountPath: /etc/app-config
          readOnly: true

  volumes:
    - name: app-config
      configMap:
        name: app-config



kubectl apply -f config-volume.yaml

# Read mounted configuration
kubectl exec config-volume-demo -- cat /etc/app-config/APP_MODE

# List all mounted keys
kubectl exec config-volume-demo -- ls -lah /etc/app-config

ConfigMap volume updates are eventually propagated, but applications must be able to reload changed files. Mounts using `subPath` do not receive automated updates.

6. Mount a Secret as Files 


# Create a Secret
kubectl create secret generic app-secret \
  --from-literal=username=admin \
  --from-literal=password='change-me'

# Inspect Secret metadata
kubectl describe secret app-secret

Pod example: 


apiVersion: v1
kind: Pod
metadata:
  name: secret-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "ls -lah /etc/secrets; sleep 3600"]
      volumeMounts:
        - name: secret-data
          mountPath: /etc/secrets
          readOnly: true

  volumes:
    - name: secret-data
      secret:
        secretName: app-secret
        defaultMode: 0400



kubectl apply -f secret-volume.yaml

# List mounted secret files
kubectl exec secret-volume-demo -- ls -lah /etc/secrets

# Read a secret file (avoid exposing it in shared terminals or logs)
kubectl exec secret-volume-demo -- cat /etc/secrets/username

Use restrictive permissions and least-privilege RBAC. Kubernetes Secrets are not automatically encrypted at rest unless encryption at rest is configured for the cluster.

7. Mount Selected ConfigMap or Secret Keys

Use `items` to expose only selected keys and control their filenames. 


volumes:
  - name: app-config
    configMap:
      name: app-config
      items:
        - key: APP_MODE
          path: settings/mode
        - key: LOG_LEVEL
          path: settings/log-level

For a Secret: 


volumes:
  - name: credentials
    secret:
      secretName: app-secret
      items:
        - key: username
          path: auth/user
        - key: password
          path: auth/password

The files appear under the volume mount path using the specified relative paths.

8. Mount Multiple Sources with a Projected Volume

Projected volumes combine sources into one directory. 


apiVersion: v1
kind: Pod
metadata:
  name: projected-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "find /etc/app -type f; sleep 3600"]
      volumeMounts:
        - name: app-files
          mountPath: /etc/app
          readOnly: true

  volumes:
    - name: app-files
      projected:
        sources:
          - configMap:
              name: app-config
          - secret:
              name: app-secret



kubectl apply -f projected-volume.yaml

# Inspect projected files
kubectl exec projected-volume-demo -- find /etc/app -type f

Projected sources can include ConfigMaps, Secrets, Downward API data, and service account tokens.

9. Mount a Specific File with subPath

Use `subPath` when a container needs one file or directory from a volume without mounting the entire volume over the target path. 


volumeMounts:
  - name: app-config
    mountPath: /etc/app/application.properties
    subPath: application.properties

Example volume definition: 


volumes:
  - name: app-config
    configMap:
      name: app-config

Important: `subPath` mounts do not receive automated updates when the source ConfigMap or Secret changes. Restart or reload the workload to consume updated content.

10. Mount a PersistentVolumeClaim 


apiVersion: v1
kind: Pod
metadata:
  name: pvc-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "echo persistent-data >> /data/test.txt; sleep 3600"]
      volumeMounts:
        - name: app-storage
          mountPath: /data

  volumes:
    - name: app-storage
      persistentVolumeClaim:
        claimName: app-pvc



# Check the claim
kubectl get pvc app-pvc

# Inspect the pod
kubectl describe pod pvc-volume-demo

# Verify mounted data
kubectl exec pvc-volume-demo -- cat /data/test.txt

The PVC must exist in the same namespace as the Pod and be compatible with the workload's storage requirements.

11. Use Multiple Volumes in One Pod

A workload can mount separate volumes for application data, configuration, credentials, and temporary files. 


apiVersion: v1
kind: Pod
metadata:
  name: multi-volume-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: data
          mountPath: /var/lib/app
        - name: config
          mountPath: /etc/app
          readOnly: true
        - name: cache
          mountPath: /tmp/cache

  volumes:
    - name: data
      emptyDir: {}
    - name: config
      configMap:
        name: app-config
    - name: cache
      emptyDir:
        sizeLimit: 500Mi

For production workloads, replace the application data `emptyDir` with a PVC if the data must survive Pod deletion.

12. Configure Volume Permissions with fsGroup

Use a Pod security context to provide a supplemental group for processes and supported mounted volumes. 


apiVersion: v1
kind: Pod
metadata:
  name: volume-permissions-demo
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
    fsGroupChangePolicy: OnRootMismatch

  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "id; touch /data/test.txt; sleep 3600"]
      volumeMounts:
        - name: app-data
          mountPath: /data

  volumes:
    - name: app-data
      emptyDir: {}



kubectl apply -f volume-permissions.yaml

# Check the process identity
kubectl exec volume-permissions-demo -- id

# Inspect file ownership
kubectl exec volume-permissions-demo -- ls -ln /data

`fsGroupChangePolicy` controls when Kubernetes applies ownership and permission changes to supported volumes. CSI drivers may handle ownership differently, including through `VOLUMEMOUNTGROUP`.

13. Mount a Volume as Read-Only

Prevent a container from writing to a mounted volume by setting `readOnly: true`. 


volumeMounts:
  - name: shared-data
    mountPath: /data
    readOnly: true

This setting applies to that container's mount. It does not automatically make every other mount of the same volume read-only.

14. Use hostPath Volumes Carefully

A `hostPath` volume mounts a path from the node filesystem. 


apiVersion: v1
kind: Pod
metadata:
  name: hostpath-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "ls -lah /host-data; sleep 3600"]
      volumeMounts:
        - name: host-data
          mountPath: /host-data
          readOnly: true

  volumes:
    - name: host-data
      hostPath:
        path: /var/log
        type: Directory

Useful `hostPath.type` values include:

  • `Directory`: path must already exist and be a directory.
  • `DirectoryOrCreate`: create the directory if missing.
  • `File`: path must already exist and be a file.
  • `FileOrCreate`: create the file if missing.

Avoid using `hostPath` for ordinary application persistence. It creates node dependencies and can expose sensitive host files. Restrict it through admission policies and workload security controls.

15. Use Downward API Data in a Volume

The Downward API can expose Pod metadata and resource information as files. 


apiVersion: v1
kind: Pod
metadata:
  name: downward-volume-demo
  labels:
    app: example
    environment: staging
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "cat /etc/pod-info/labels; sleep 3600"]
      volumeMounts:
        - name: pod-info
          mountPath: /etc/pod-info
          readOnly: true

  volumes:
    - name: pod-info
      downwardAPI:
        items:
          - path: labels
            fieldRef:
              fieldPath: metadata.labels
          - path: name
            fieldRef:
              fieldPath: metadata.name



kubectl apply -f downward-volume.yaml

# Inspect Pod metadata exposed as files
kubectl exec downward-volume-demo -- cat /etc/pod-info/labels
kubectl exec downward-volume-demo -- cat /etc/pod-info/name

16. Mount a ServiceAccount Token with a Projected Volume

Projected service account tokens provide short-lived credentials for applications that need to authenticate to the Kubernetes API. 


volumes:
  - name: api-credentials
    projected:
      sources:
        - serviceAccountToken:
            path: token
            expirationSeconds: 3600
            audience: https://kubernetes.default.svc

Mount it in a container: 


volumeMounts:
  - name: api-credentials
    mountPath: /var/run/secrets/tokens
    readOnly: true

Use an appropriate audience and RBAC permissions. Applications should reload rotated tokens rather than assuming a token remains valid indefinitely.

17. Use CSI Ephemeral Volumes

Some CSI drivers support ephemeral inline volumes defined directly in a Pod. 


apiVersion: v1
kind: Pod
metadata:
  name: csi-ephemeral-demo
spec:
  containers:
    - name: app
      image: busybox
      command: ["sh", "-c", "sleep 3600"]
      volumeMounts:
        - name: scratch
          mountPath: /scratch

  volumes:
    - name: scratch
      csi:
        driver: example.csi.driver
        volumeAttributes:
          exampleParameter: exampleValue

The driver name and attributes above are placeholders. Replace them with values supported by an installed CSI driver. Not every CSI driver supports inline ephemeral volumes.

# List mounted files
kubectl exec <pod-name> -- mount

# Inspect filesystem capacity
kubectl exec <pod-name> -- df -h

# Inspect directory permissions
kubectl exec <pod-name> -- ls -lah <mount-path>

# Inspect ownership
kubectl exec <pod-name> -- ls -ln <mount-path>

# Check available disk space
kubectl exec <pod-name> -- df -h <mount-path>

# Inspect a specific file

If the container image does not include diagnostic utilities, use an approved ephemeral debug container or another suitable troubleshooting image.

19. Debug Volume Mount Failures 


# Inspect pod events and mount errors
kubectl describe pod <pod-name>

# Show recent namespace events
kubectl get events --sort-by=.metadata.creationTimestamp

# Inspect pod status and conditions
kubectl get pod <pod-name> -o yaml

# Inspect PVC status
kubectl get pvc

# Inspect PV status
kubectl get pv

# Inspect storage classes
kubectl get storageclass

# Inspect node details
kubectl describe node <node-name>

Common errors:

Error Possible cause
`MountVolume.SetUp failed` Invalid volume source or mount setup failure
`persistentvolumeclaim not found` Missing PVC or wrong namespace
`permission denied` UID/GID, filesystem permissions, or security context mismatch
`read-only file system` Read-only mount or backend filesystem state
`no such file or directory` Incorrect mount path, key, or source file
`Multi-Attach error` Volume attachment constraints or conflicting consumers
Pod stuck in `ContainerCreating` Volume provisioning, attachment, or mount failure

20. Troubleshoot Permission Problems 


# Inspect the container user
kubectl exec <pod-name> -- id

# Inspect directory ownership
kubectl exec <pod-name> -- ls -ldn <mount-path>

# Inspect file permissions
kubectl exec <pod-name> -- ls -ln <mount-path>

# Test write access
kubectl exec <pod-name> -- sh -c 'touch <mount-path>/.write-test'

# Remove the test file
kubectl exec <pod-name> -- rm -f <mount-path>/.write-test

Check these items when writes fail:

  1. Container `runAsUser` and `runAsGroup`.
  2. Pod-level `fsGroup`.
  3. Volume and filesystem ownership.
  4. Read-only mount settings.
  5. CSI driver mount and ownership behavior.
  6. Security policies and backend access controls.

Do not solve permission problems by blindly running containers as root or applying world-writable permissions.

21. Inspect StatefulSet Volume Mounts

StatefulSets commonly use `volumeClaimTemplates` to provide one PVC per replica. 


# Inspect StatefulSets
kubectl get statefulsets

# Inspect a StatefulSet
kubectl describe statefulset <statefulset-name>

# List PVCs
kubectl get pvc

# Inspect generated PVCs
kubectl get pvc -l app=<app-label>

# Inspect the StatefulSet specification
kubectl get statefulset <statefulset-name> -o yaml

Example: 


apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: database
spec:
  serviceName: database
  replicas: 2
  selector:
    matchLabels:
      app: database
  template:
    metadata:
      labels:
        app: database
    spec:
      containers:
        - name: database
          image: busybox
          command: ["sh", "-c", "sleep 3600"]
          volumeMounts:
            - name: database-data
              mountPath: /var/lib/database
  volumeClaimTemplates:
    - metadata:
        name: database-data
      spec:
        accessModes:
          - ReadWriteOnce
        storageClassName: standard
        resources:
          requests:
            storage: 10Gi

The StorageClass must exist and support the requested volume. Each StatefulSet replica receives its own claim.

24. Practical Volume Design Rules

  • Use `emptyDir` for temporary data shared within a Pod.
  • Use PVCs for data that must survive Pod deletion.
  • Use ConfigMaps for non-sensitive configuration files.
  • Use Secrets for credentials and sensitive configuration.
  • Use projected volumes when multiple sources should appear under one directory.
  • Use `readOnly: true` for mounts that do not need writes.
  • Use `subPath` deliberately, remembering that it does not receive automated ConfigMap or Secret updates.
  • Use `fsGroup` and appropriate ownership settings instead of running every container as root.
  • Avoid `hostPath` unless node-level access is genuinely required.
  • Set resource requests and limits for memory-backed `emptyDir` and account for ephemeral storage consumption.
  • Test volume behavior when Pods restart, move between nodes, or are recreated.
  • Keep backups independent of the lifecycle of the Pod and its volume.

Core principle: A Kubernetes volume is defined at the Pod level and mounted into containers. Choosing the correct volume type, mount path, permissions, and lifecycle behavior is essential for reliable workloads.

Beginner

Q1: What is a Kubernetes volume?

A Kubernetes volume is a storage object mounted into a Pod so containers can use persistent or temporary storage.

Q2: Why do Pods need volumes?

Pods often need storage for configuration, state, logs, caches, or database data.

Q3: What is a container filesystem?

A container filesystem is the read/write root filesystem used by a container process.

Q4: Why is container filesystem not sufficient for persistent state?

Because container filesystems are generally ephemeral and tied to the container lifecycle.

Q5: What is an emptyDir volume?

An emptyDir volume is created when a pod starts and exists as long as the pod remains alive.

Q6: Why use emptyDir?

It is useful for temporary or shared data between containers in the same pod.

Q7: What is a hostPath volume?

A hostPath volume mounts a path from the worker node filesystem into the pod.

Q8: Why is hostPath risky?

Because it exposes node filesystem content to the pod and can create security or portability problems.

Q9: What is a ConfigMap volume?

A ConfigMap volume mounts configuration data from a Kubernetes ConfigMap into files in the pod.

Q10: What is a Secret volume?

A Secret volume mounts sensitive data from a Kubernetes Secret into files in the pod.

Q11: What is a projected volume?

A projected volume combines multiple config or secret sources into a single mounted directory.

Q12: Why use projected volumes?

To mount several sources into one path without more complicated container setup.

Q13: What is a PersistentVolume?

A PersistentVolume (PV) is cluster-scoped storage that can be bound to a pod via a claim.

Q14: What is a PersistentVolumeClaim?

A PersistentVolumeClaim (PVC) is a request for storage made by a pod or workload.

Q15: What is the relation between PVC and PV?

A PVC binds to a compatible PV, which then provides storage to the pod.

Q16: Why do PVCs matter?

They abstract the storage backend and make application requests declarative.

Q17: What is a volume mount?

A volume mount attaches a volume to a specific path inside a container.

Q18: What is `mountPath`?

`mountPath` is the mount point inside the container filesystem.

Q19: What is a volume name?

A volume name is the logical name used inside the pod spec for a mounted volume.

Q20: Why are volume names important?

Because they connect the volume definition in pod spec to the mount configuration inside the container.

Q21: What is a StatefulSet?

A StatefulSet is a workload for stateful applications and often uses persistent volume claims per pod.

Q22: Why are StatefulSets tied to volumes?

Because stateful apps often need resilient and stable storage that survives pod restarts.

Q23: What is a volumeClaimTemplate?

A volumeClaimTemplate is used by a StatefulSet to dynamically create PVCs for each pod.

Q24: Why is storage important for databases?

Databases usually require durable storage for their data and metadata.

Q25: What is a storage class?

A StorageClass defines the storage provisioner and rules for dynamic creation of PVs.

Q26: Why use a StorageClass?

It allows Kubernetes to dynamically provision storage without manual PV creation.

Q27: What is dynamic provisioning?

Dynamic provisioning creates a PV automatically when a PVC is created.

Q28: What is static provisioning?

Static provisioning means a cluster admin manually creates a PV before the workload requests it.

Q29: What is a provisioner?

A provisioner is the controller or plugin that creates the underlying storage resource.

Q30: What is CSI?

CSI (Container Storage Interface) is the standard interface used by Kubernetes storage plugins.

Q31: Why is CSI important?

It standardizes how storage systems integrate with Kubernetes.

Q32: What is a local volume?

A local volume is backed by storage local to a specific node.

Q33: Why are local volumes sometimes used?

Because they can provide low-latency storage for high-performance workloads.

Q34: What is a network-attached storage volume?

A network-attached volume is backed by storage reached over the network, often via NFS or block storage.

Q35: What is cloud block storage?

Cloud block storage is storage provided by cloud providers as portable block devices.

Q36: Why do cloud infrastructures use block storage?

Because many workloads, especially databases, need block semantics and high performance.

Q37: What is ReadWriteOnce?

ReadWriteOnce means a volume can be mounted read-write by a single node at a time.

Q38: What is ReadOnlyMany?

ReadOnlyMany means many nodes can mount the same volume read-only.

Q39: What is ReadWriteMany?

ReadWriteMany means many nodes can mount the same volume with read-write access.

Q40: Why do access modes matter?

They define how many nodes can access a storage volume and in what mode.

Q41: What is a PVC size?

PVC size specifies the requested storage size, such as 10Gi.

Q42: What is a PV size?

The PV size is the actual capacity of the underlying storage resource.

Q43: Why is capacity important?

Because workloads need enough space for data, logs, and future growth.

Q44: What is volume expansion?

Volume expansion increases a PV or PVC size after the fact.

Q45: Why do operators care about expansion?

Because workloads often grow over time and need additional storage.

Q46: What is backup and restore of Kubernetes volumes?

It means making copies of the data on a volume and restoring it to another storage object.

Q47: What is a snapshot?

A snapshot is a point-in-time copy of a volume.

Q48: Why are snapshots useful?

They allow backups, cloning, and recovery of volume contents.

Q49: What is a clone?

A clone is a new volume created from an existing snapshot or data set.

Q50: What is a volume mount path?

It is the directory inside a container where the volume is attached.

Q51: Why is `subPath` used?

A `subPath` mount attaches only a specific subdirectory or file from a volume.

Q52: Why use `subPath` carefully?

Because it can be confusing and may not behave as expected if the underlying directory structure changes.

Q53: What is a volume lifecycle?

It includes creation, attachment, use, release, and cleanup.

Q54: Why is lifecycle management important?

Because volumes can persist beyond the lifetime of individual pods and need careful governance.

Q55: What is a volume reclaim policy?

A reclaim policy describes what happens when a PV is released: retain, delete, or recycle.

Q56: What is Retain?

Retain preserves the underlying storage after the PV is released.

Q57: What is Delete?

Delete deletes the backing storage resource when the PV is released.

Q58: What is Recycle?

Recycle is an older behavior that makes the volume reusable, though it is less common in modern Kubernetes.

Q59: What is a PVC pending state?

A PVC remains pending until a compatible PV is bound or a provisioner creates one.

Q60: Why would a PVC be pending?

Possible reasons include unavailable storage classes, no matching volume, or provisioning delays.

Q61: What is `volumeMode`?

`volumeMode` is either Filesystem or Block and defines how the storage is exposed.

Q62: What is filesystem volume mode?

It exposes the storage as a filesystem mount point.

Q63: What is block volume mode?

It exposes the storage as a raw block device.

Q64: Why is block mode relevant?

Some database and storage systems require block access.

Q65: What is a pod with multiple volumes?

A pod can mount several volumes at once, such as config, secret, and persistent data.

Q66: Why mount multiple volumes?

Because different application parts may need different kinds of data.

Q67: What is an application state volume?

A volume that stores long-lived state such as database files or user uploads.

Q68: What is a cache volume?

A cache volume stores temporary or reusable data to improve performance.

Q69: What is a temp volume?

A temp volume is often used for scratch or transient operations.

Q70: What is the purpose of volumes for log storage?

To keep logs accessible even after pod replacement or restart.

Q71: Why are logs in volumes helpful?

They support debugging, monitoring, and retention decisions.

Q72: What is a stateful workload?

A stateful workload depends on persistent storage and usually stable identity.

Q73: What is a stateless workload?

A stateless workload does not rely on persistent local state.

Q74: Why are stateful app volumes important for reliability?

Because without persistent storage, data can be lost when the pod moves or restarts.

Q75: What is an `emptyDir` lifecycle tied to the pod?

An `emptyDir` is created when a pod starts and removed when the pod is deleted.

Q76: What is a `hostPath` lifecycle tied to the node?

A `hostPath` points to a path on the worker host and is not automatically portable.

Q77: What is a volume for application secrets?

Used to inject TLS certs, API keys, or other sensitive files into the pod at runtime.

Q78: What happens if a pod is rescheduled?
