Kubernetes ConfigMaps & Secrets Command Handbook:

1. ConfigMap Creation & Management 


# Create ConfigMap from literal values
kubectl create configmap app-config \
  --from-literal=APP_ENV=development \
  --from-literal=LOG_LEVEL=debug

# Create ConfigMap from a file
kubectl create configmap app-config \
  --from-file=application.properties

# Create ConfigMap from a directory
kubectl create configmap app-config \
  --from-file=./config/

# Create ConfigMap from environment file
kubectl create configmap app-config \
  --from-env-file=.env

# List ConfigMaps
kubectl get configmaps
kubectl get cm

# List ConfigMaps across namespaces
kubectl get cm -A

# Describe ConfigMap
kubectl describe configmap app-config

# Display ConfigMap YAML
kubectl get configmap app-config -o yaml

# Display ConfigMap JSON
kubectl get configmap app-config -o json

# Delete ConfigMap
kubectl delete configmap app-config

2. ConfigMap Inspection & Updates 


# Display ConfigMap data
kubectl get cm app-config -o yaml

# Display a specific ConfigMap value
kubectl get cm app-config \
  -o jsonpath='{.data.APP_ENV}'

# Display all ConfigMap keys
kubectl get cm app-config \
  -o jsonpath='{.data}'

# Edit ConfigMap interactively
kubectl edit configmap app-config

# Update a ConfigMap value
kubectl patch configmap app-config \
  --type=merge \
  -p '{"data":{"LOG_LEVEL":"info"}}'

# Add a new ConfigMap key
kubectl patch configmap app-config \
  --type=merge \
  -p '{"data":{"APP_VERSION":"1.0"}}'

# Replace ConfigMap from YAML
kubectl replace -f configmap.yaml

# Apply updated ConfigMap
kubectl apply -f configmap.yaml

# Watch ConfigMap changes
kubectl get configmap app-config -w

# Display ConfigMap labels
kubectl get cm app-config --show-labels

# Add label to ConfigMap
kubectl label configmap app-config environment=production

3. Secret Creation & Management 


# Create generic Secret
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password=change-me

# Create Secret from file
kubectl create secret generic db-secret \
  --from-file=password=./password.txt

# Create Secret from environment file
kubectl create secret generic db-secret \
  --from-env-file=.env

# Create Secret from multiple files
kubectl create secret generic app-secret \
  --from-file=username=./username.txt \
  --from-file=password=./password.txt

# List Secrets
kubectl get secrets

# List Secrets across namespaces
kubectl get secrets -A

# Describe Secret
kubectl describe secret db-secret

# Display Secret metadata and encoded data
kubectl get secret db-secret -o yaml

# Delete Secret
kubectl delete secret db-secret

# Create Secret YAML without applying it
kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --dry-run=client -o yaml

4. Secret Inspection & Decoding 


# Display Secret metadata
kubectl get secret db-secret

# Display Secret type
kubectl get secret db-secret \
  -o jsonpath='{.type}'

# Display Secret keys
kubectl get secret db-secret \
  -o jsonpath='{.data}'

# Display encoded username
kubectl get secret db-secret \
  -o jsonpath='{.data.username}'

# Decode a specific Secret value
kubectl get secret db-secret \
  -o jsonpath='{.data.password}' | base64 --decode

# Decode username
kubectl get secret db-secret \
  -o jsonpath='{.data.username}' | base64 --decode

# Display Secret labels
kubectl get secret db-secret --show-labels

# Edit Secret interactively
kubectl edit secret db-secret

# Export Secret YAML
kubectl get secret db-secret -o yaml

Security warning: Decoding a Secret exposes its plaintext value in terminal output. Avoid using these commands in shared terminals, CI logs, or recorded sessions. Base64 is encoding, not encryption.

5. ConfigMap Environment Variable Injection 


# Display deployment configuration
kubectl get deployment nginx -o yaml

# Create deployment
kubectl create deployment nginx --image=nginx

# Inject one ConfigMap key as environment variable
kubectl set env deployment/nginx \
  --from=configmap/app-config

# Display environment variables
kubectl exec deployment/nginx -- printenv

# Display a specific environment variable
kubectl exec deployment/nginx -- printenv APP_ENV

# Display deployment environment configuration
kubectl describe deployment nginx

# Remove an environment variable
kubectl set env deployment/nginx APP_ENV-

# Restart deployment after ConfigMap changes
kubectl rollout restart deployment/nginx

6. Secret Environment Variable Injection 


# Inject all Secret keys as environment variables
kubectl set env deployment/nginx \
  --from=secret/db-secret

# Inject a specific Secret key
kubectl set env deployment/nginx \
  --from=secret/db-secret \
  --prefix=DB_

# Display deployment environment configuration
kubectl describe deployment nginx

# Display environment variables inside container
kubectl exec deployment/nginx -- printenv

# Restart deployment after Secret changes
kubectl rollout restart deployment/nginx

# Check rollout status
kubectl rollout status deployment/nginx

Note: Environment variables are populated when a container starts. Updating the referenced ConfigMap or Secret does not update existing process environment variables. Restart the workload to load new values.

7. ConfigMap Volume Mounts 


# Apply ConfigMap manifest
kubectl apply -f configmap.yaml

# Apply Pod manifest with ConfigMap volume
kubectl apply -f pod-configmap.yaml

# Display pod details
kubectl describe pod configmap-pod

# Display mounted ConfigMap files
kubectl exec configmap-pod -- ls -l /etc/config

# Read mounted configuration file
kubectl exec configmap-pod -- cat /etc/config/application.properties

# Display ConfigMap volume information
kubectl get pod configmap-pod -o yaml

# Display ConfigMap volume mounts
kubectl get pod configmap-pod \
  -o jsonpath='{.spec.containers[*].volumeMounts}'

# Delete pod
kubectl delete pod configmap-pod

Example ConfigMap volume configuration: 


apiVersion: v1
kind: Pod
metadata:
  name: configmap-pod
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts:
        - name: config-volume
          mountPath: /etc/config
  volumes:
    - name: config-volume
      configMap:
        name: app-config

apiVersion: v1
kind: Pod

  name: secret-pod

  containers:
    - name: app
      image: nginx
      volumeMounts:

9. Projected Volumes 


# Display projected volume configuration
kubectl get pod app-pod -o yaml

# Apply projected volume manifest
kubectl apply -f projected-volume.yaml

# Inspect pod
kubectl describe pod app-pod

# List projected files
kubectl exec app-pod -- ls -la /etc/app-config

# Read ConfigMap file
kubectl exec app-pod -- cat /etc/app-config/application.properties

# Read Secret file
kubectl exec app-pod -- cat /etc/app-config/password

# Delete pod
kubectl delete pod app-pod

Example projected volume: 


apiVersion: v1
kind: Pod
metadata:
  name: projected-pod
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts:
        - name: app-config
          mountPath: /etc/app-config
          readOnly: true
  volumes:
    - name: app-config
      projected:
        sources:
          - configMap:
              name: app-config
          - secret:
              name: db-secret

  --type=merge \
  -p '{"data":{"LOG_LEVEL":"info"}}'

  --type=merge \
  -p '{"stringData":{"password":"new-password"}}'

# Display updated Secret metadata
kubectl describe secret db-secret

# Restart deployment
kubectl rollout restart deployment/nginx

# Monitor rollout
kubectl rollout status deployment/nginx

# Display deployment pods
kubectl get pods -l app=nginx

# Check rollout history
kubectl rollout history deployment/nginx

# Roll back deployment
kubectl rollout undo deployment/nginx

Important update behavior:

Consumption method Update behavior
ConfigMap environment variable Requires container restart
Secret environment variable Requires container restart
ConfigMap volume mount Eventually updated
Secret volume mount Eventually updated
ConfigMap / Secret using `subPath` Does not receive automatic updates
Projected volume Eventually updated, subject to source update behavior

# Display Secret type
kubectl get secret registry-secret \
  -o jsonpath='{.type}'

Example `kustomization.yaml`: 

apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

configMapGenerator:
  - name: app-config
    literals:
      - APP_ENV=production
      - LOG_LEVEL=info

  - name: db-secret
    literals:
      - username=admin
      - password=placeholder

The generated resource names normally include a content hash, which helps trigger workload updates when generated configuration changes.

Do not commit real Secret values to Git. Use an appropriate encrypted or external secret-management workflow.

17. RBAC & ConfigMap / Secret Permissions 


# List Roles
kubectl get roles -A

# List ClusterRoles
kubectl get clusterroles

# List RoleBindings
kubectl get rolebindings -A

# List ClusterRoleBindings
kubectl get clusterrolebindings

# Check permission to read ConfigMaps
kubectl auth can-i get configmaps

# Check permission to list Secrets
kubectl auth can-i list secrets

# Check permission to read Secrets in production
kubectl auth can-i get secrets -n production

# Check permission as another user
kubectl auth can-i get secrets --as=developer

# Check permissions for a ServiceAccount
kubectl auth can-i get secrets \
  --as=system:serviceaccount:production:app-user \
  -n production

# List current user's permissions
kubectl auth can-i --list

Example namespace-scoped Role: 


apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: config-reader
  namespace: production
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]

Example RoleBinding: 


apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: config-reader-binding
  namespace: production
subjects:
  - kind: ServiceAccount
    name: app-user
    namespace: production
roleRef:
  kind: Role
  name: config-reader
  apiGroup: rbac.authorization.k8s.io

Avoid granting broad Secret permissions. In particular, `list` and `watch` can expose the values of Secrets, not just their names.

These commands are mainly relevant to self-managed Kubernetes control planes. 


# Check API server configuration

# Inspect API server command arguments

  /etc/kubernetes/manifests/kube-apiserver.yaml

# Check etcd configuration
kubectl describe pod etcd-node-name -n kube-system

kubectl get --raw='/readyz?verbose'

# Inspect Secret metadata
kubectl get secrets -A

Example encryption configuration structure: 


apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: REPLACE_WITH_BASE64_ENCODED_KEY
      - identity: {}

Note: This is an illustrative configuration, not a ready-to-deploy production file. Encryption provider configuration must be managed carefully, and existing Secrets must be rewritten after enabling encryption so that they are stored encrypted. Prefer a supported KMS integration for production environments where appropriate.

Important Security Rules:

  1. Never commit plaintext credentials, private keys, or production passwords to Git.
  2. Base64 encoding does not encrypt Kubernetes Secrets.
  3. Enable encryption at rest for Secrets in etcd.
  4. Use RBAC and least-privilege permissions to control Secret access.
  5. Prefer external secret managers for centralized credential lifecycle management.
  6. Rotate credentials regularly and coordinate application reloads.
  7. Avoid exposing Secret values through terminal output, shell history, or CI/CD logs.
  8. Use immutable ConfigMaps and Secrets when configuration changes should be explicit and controlled.
  9. Remember that ConfigMaps and Secrets are namespace-scoped resources.

  10. Treat the Kubernetes control plane, etcd, kubelet, and container runtime as part of the security boundary.

Beginner

Q1: What is a Kubernetes ConfigMap?

A ConfigMap is a Kubernetes API object used to store non-sensitive configuration data for pods.

Q2: Why use ConfigMaps?

ConfigMaps allow you to decouple configuration from application code and images.

Q3: What is a Secret in Kubernetes?

A Secret is a Kubernetes API object used to store sensitive information such as passwords, tokens, or TLS keys.

Q4: Why use Secrets?

Secrets help keep sensitive data out of source code and container images.

Q5: What is configuration in Kubernetes?

Configuration is the environment-specific or runtime-specific settings an application needs to run properly.

Q6: What is runtime configuration?

Runtime configuration includes environment variables, settings files, and dynamic data used while the app runs.

Q7: What is a pod in Kubernetes?

A pod is the smallest deployable unit in Kubernetes and usually contains one or more tightly-coupled containers.

Q8: How do pods consume ConfigMaps?

Pods can consume ConfigMaps through environment variables, command-line arguments, or mounted files.

Q9: How do pods consume Secrets?

Pods consume Secrets similarly to ConfigMaps: as environment variables, mounted files, or projected volumes.

Q10: What is the difference between ConfigMap and Secret?

A ConfigMap is for non-sensitive config. A Secret is for sensitive config and is stored in a way that is handled more securely.
