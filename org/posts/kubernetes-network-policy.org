*5. Creating & Applying NetworkPolicies*

NetworkPolicies are defined using Kubernetes YAML manifests.

#+BEGIN_SRC bash

# Apply a NetworkPolicy manifest
kubectl apply -f network-policy.yaml

# Apply all YAML files in a directory
kubectl apply -f ./network-policies/

# Apply policies from a URL
kubectl apply -f https://example.com/network-policy.yaml

# Validate manifest without applying changes
kubectl apply --dry-run=server -f network-policy.yaml

# Display changes before applying
kubectl diff -f network-policy.yaml

# Create a NetworkPolicy declaratively
kubectl create -f network-policy.yaml

# Reapply updated configuration
kubectl apply -f network-policy.yaml

# Apply policy in a specific namespace
kubectl apply -n production -f network-policy.yaml

# Delete a NetworkPolicy manifest
kubectl delete -f network-policy.yaml

# Delete a specific NetworkPolicy
kubectl delete networkpolicy my-policy

#+END_SRC


*6. Default Deny NetworkPolicies*

Default-deny policies are commonly used to implement zero-trust network segmentation.

Deny all ingress traffic:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress

#+END_SRC


Deny all egress traffic:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Egress

#+END_SRC

Deny all ingress and egress traffic:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress

#+END_SRC

#+BEGIN_SRC bash

# Apply default-deny policies
kubectl apply -f default-deny-ingress.yaml
kubectl apply -f default-deny-egress.yaml
kubectl apply -f default-deny-all.yaml

# Inspect default-deny policies
kubectl get networkpolicy -n production

# Describe default-deny policy
kubectl describe networkpolicy default-deny-all -n production

#+END_SRC

Note: Default-deny egress also blocks DNS unless a separate DNS allow policy is configured. Apply these policies carefully to avoid disrupting existing workloads.

*7. Allow Ingress Traffic*

Ingress policies control which sources can connect to selected Pods.

Allow traffic from frontend Pods to backend Pods:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080

#+END_SRC

#+BEGIN_SRC bash

# Apply ingress policy
kubectl apply -f allow-frontend-to-backend.yaml

# Inspect ingress policy
kubectl describe networkpolicy allow-frontend-to-backend

# Check selected backend Pods
kubectl get pods -l app=backend

# Check frontend Pods
kubectl get pods -l app=frontend

#+END_SRC

*9. DNS Egress & NetworkPolicy Configuration*

DNS must be explicitly permitted when workloads are isolated for egress.
A common CoreDNS configuration uses the k8s-app=kube-dns label in the kube-system namespace. Verify the actual labels in your cluster first.

#+BEGIN_SRC bash

# Find DNS Pods
kubectl get pods -n kube-system -l k8s-app=kube-dns

# Inspect DNS services
kubectl get services -n kube-system

# Display DNS Pod labels
kubectl get pods -n kube-system --show-labels

#+END_SRC


Allow DNS traffic:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53

#+END_SRC

#+BEGIN_SRC bash

# Apply DNS policy
kubectl apply -f allow-dns-egress.yaml

# Check DNS Pods
kubectl get pods -n kube-system

# Check DNS service
kubectl get svc -n kube-system

# Inspect DNS policy
kubectl describe networkpolicy allow-dns-egress

#+END_SRC

Note: DNS Pod labels and DNS architecture can differ between clusters. Adjust the selectors to match your actual DNS deployment.

*10. Namespace & Pod Selector Configuration*

Namespace selectors and Pod selectors allow policies to control communication across namespace boundaries.

#+BEGIN_SRC bash

# Label frontend namespace
kubectl label namespace frontend team=frontend

# Label backend namespace
kubectl label namespace backend team=backend

# Label database namespace
kubectl label namespace database team=database

# Verify namespace labels
kubectl get namespaces --show-labels

# Find Pods by namespace
kubectl get pods -n frontend
kubectl get pods -n backend
kubectl get pods -n database

#+END_SRC

Allow traffic from selected Pods in another namespace:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-namespace
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              team: frontend
          podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080

#+END_SRC


Important: When namespaceSelector and podSelector are in the same list item, both conditions must match. Separate list items represent alternative allowed sources.

*11. IPBlock & CIDR Configuration*

IPBlock allows traffic based on specified IP ranges.

#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-external-api
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Egress
  egress:
    - to:
        - ipBlock:
            cidr: 203.0.113.0/24
            except:
              - 203.0.113.128/25
      ports:
        - protocol: TCP
          port: 443

#+END_SRC

#+BEGIN_SRC bash

# Apply IPBlock policy
kubectl apply -f allow-external-api.yaml

# Inspect IPBlock policy
kubectl describe networkpolicy allow-external-api

# Check policy configuration
kubectl get networkpolicy allow-external-api -o yaml

#+END_SRC


Note: 203.0.113.0/24 is a documentation-only address range. Replace it with the actual external network range required by your application. IPBlock is generally intended for external IP ranges rather than dynamically assigned Pod IPs.

*13. NetworkPolicy Testing & Connectivity Validation*

Testing is essential to verify that policies enforce the expected traffic restrictions.

#+BEGIN_SRC bash

# Create frontend test Pod
kubectl run frontend-test \
  --image=busybox:1.36 \
  --labels="app=frontend" \
  --restart=Never \
  -- sleep 3600

# Create backend test Pod
kubectl run backend-test \
  --image=busybox:1.36 \
  --labels="app=backend" \
  --restart=Never \
  -- sleep 3600

# List test Pods
kubectl get pods --show-labels

# Test frontend-to-backend connectivity
kubectl exec frontend-test -- \
  wget -T 3 -qO- http://backend-service:8080

# Test DNS resolution
kubectl exec frontend-test -- \
  nslookup backend-service

# Test TCP connectivity
kubectl exec frontend-test -- \
  nc -zvw 3 backend-service 8080

# Inspect test Pod
kubectl describe pod frontend-test

# Remove test Pods
kubectl delete pod frontend-test backend-test

#+END_SRC

Note: The test commands assume that the corresponding test images contain the required utilities and that backend-service exists.

*16. Advanced NetworkPolicy Rules & Port Ranges*

NetworkPolicies support TCP, UDP, and SCTP protocol definitions, subject to network plugin support.

Allow a range of TCP ports:
#+BEGIN_SRC yaml

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-port-range
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - ports:
        - protocol: TCP
          port: 8000
          endPort: 8100

#+END_SRC

#+BEGIN_SRC bash

# Apply port range policy
kubectl apply -f allow-port-range.yaml

# Inspect port range policy
kubectl describe networkpolicy allow-port-range

# Display YAML
kubectl get networkpolicy allow-port-range -o yaml

#+END_SRC

endPort requires a numeric starting port and a numeric ending port greater than or equal to the starting port. Network plugin support should be verified.

*21. Best Practices for Kubernetes NetworkPolicy & DevSecOps*

1. Start with default-deny ingress and egress policies where appropriate.
2. Allow only explicitly required network communication.
3. Always permit necessary DNS traffic when egress is restricted.
4. Use consistent Pod labels and namespace labels.
5. Apply least-privilege rules for application and database workloads.
6. Restrict database access to authorized application Pods.
7. Avoid unnecessary wildcard selectors and broad CIDR ranges.
8. Validate NetworkPolicy support in your CNI plugin.
9. Test connectivity before deploying policies to production.
10. Use separate policies for ingress and egress where practical.
11. Monitor network traffic and investigate unexpected connection failures.
12. Keep NetworkPolicy manifests under version control.
13. Use CI/CD validation before applying production policies.
14. Review policies regularly as application dependencies change.
15. Keep management and administrative ports private.
16. Document required network paths between application tiers.
17. Back up policies before making significant changes.
18. Coordinate NetworkPolicy changes with ingress controllers and service infrastructure.
19. Use CNI-specific observability tools for packet drops and policy debugging.
20. Treat NetworkPolicies as one layer of defense, not a replacement for application security, authentication, or authorization.

* Beginner

** Q1: What is a Kubernetes NetworkPolicy?
A NetworkPolicy is a Kubernetes resource that controls how Pods can communicate with each other and with network endpoints.

** Q2: Why do we need NetworkPolicies?
They provide network-level isolation and enforce who can talk to whom inside the cluster.

** Q3: What is network segmentation?
Network segmentation divides network traffic into trust zones or boundaries to reduce lateral movement.

** Q4: Why is segmentation important?
It helps restrict blast radius if a workload is compromised.

** Q5: What is a Pod policy?
A Pod policy defines network traffic rules for a set of Pods.

** Q6: What are ingress rules?
Ingress rules define which connections are allowed into a Pod.

** Q7: What are egress rules?
Egress rules define which connections a Pod is allowed to initiate outbound.

** Q8: What is default-deny?
Default-deny means no traffic is allowed unless a specific policy allows it.

** Q9: Why is default-deny a common secure posture?
It reduces accidental or malicious network access to a workload.

** Q10: What does NetworkPolicy apply to?
A NetworkPolicy applies to Pods selected by labels and optional namespace selectors.

** Q11: What is a `podSelector`?
A `podSelector` selects the Pods that the policy applies to.

** Q12: What is a `policyTypes` field?
It defines whether the policy applies to ingress, egress, or both.

** Q13: What is an ingress rule?
An ingress rule allows incoming connections to matching Pods.

** Q14: What is an egress rule?
An egress rule allows outgoing connections from matching Pods.

** Q15: What are `from` rules?
`from` rules specify who may connect to the selected Pods in ingress policies.

** Q16: What are `to` rules?
`to` rules specify what destinations are allowed for egress traffic.

** Q17: What is a namespace selector?
A namespace selector matches Pods in specific namespaces.

** Q18: What is a pod selector in a network policy?
A pod selector can select specific workloads in the same or other namespaces.

** Q19: What is an IPBlock?
An IPBlock allows or denies traffic to and from specific CIDR ranges.

** Q20: What is a CIDR?
A CIDR is a network range such as 10.0.0.0/8 or 192.168.1.0/24.

** Q21: Why use IPBlock?
It allows policies to permit or deny traffic to known external networks or internal ranges.

** Q22: What is a namespace + pod selector combination?
It selects Pods in specific namespaces that match labels, useful for multi-tenant policies.

** Q23: Why are NetworkPolicies namespaced?
A NetworkPolicy is created in a namespace and applies only to Pods in that namespace unless cross-namespace selectors are used.

** Q24: What is a Pod not selected by any policy?
If no policies apply, the default pod network behavior depends on the cluster CNI and default policy settings.

** Q25: What is the default network behavior without NetworkPolicies?
Many clusters allow unrestricted pod-to-pod communication unless a CNI or security policy restricts it.

** Q26: What is a CNI?
CNI (Container Network Interface) is the network plugin standard for Kubernetes networking.

** Q27: Why does CNI matter for NetworkPolicies?
Because NetworkPolicy support depends on the CNI plugin implementing the policy enforcement.

** Q28: What is a network plugin with NetworkPolicy support?
Examples include Calico, Cilium, Antrea, and others.

** Q29: What is an ingress allowlist?
An ingress allowlist is a set of allowed sources for incoming traffic to a service or pod.

** Q30: What is an egress allowlist?
An egress allowlist is a set of allowed destinations for outbound traffic.

** Q31: What is a default allow policy?
